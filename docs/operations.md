# Operations runbook

## Environments

Use separate Firebase projects, service accounts, App Hosting backends, and environment files for staging and production. Never point a local or staging deployment at the production Firebase project. Set `APP_ENV` to `development`, `staging`, or `production`, and verify `FIREBASE_PROJECT_ID` before every deployment.

## Firestore backups

Enable scheduled Firestore exports in Google Cloud for the production project, writing to a versioned, retention-protected Cloud Storage bucket in the same location. Grant the Firestore service agent access to the bucket. Run a restore drill into staging at least quarterly and record its duration and result.

Recommended schedule and retention:

- Daily export retained for 35 days.
- Weekly export retained for 13 weeks.
- Monthly export retained for 12 months.

Before destructive administration or a large import, create an on-demand export and record its export path in the change ticket.

## Monitoring and repair

Forward server errors and failed Firebase operations to the production error-monitoring service, tagged with `APP_ENV`, release SHA, actor ID, operation type, shop ID, and reporting month. Do not attach workbook contents or personal data.

Failed dashboard projection refreshes are stored in `maintenanceJobs` with type `dashboard-summary-refresh`. An administrator can invoke `retryPendingDashboardSummaryJobs`; use `rebuildDashboardSummaryMonths` for an explicit month rebuild. Alert when a pending job is older than 15 minutes or has three failed attempts.

Shop report selectors read `shops/{shopId}/metadata/performanceIndex`. Older shops build this document on first access. Performance mutations mark it dirty and refresh it alongside dashboard summaries; while dirty, reads fall back to a projected performance query. Retry pending dashboard projection jobs to repair an index left dirty after a failed refresh.

Month-scoped performance mutations refresh selector entries only for their affected months, retaining other months and superseded import versions. Dirty markers union pending months when saves overlap; an unscoped or legacy marker requires a full scan. The refresh token and document version prevent an older refresh from marking newer work clean. Missing, invalid or oversized indexes retain full projected reads and the existing repair path.

Dashboard month selectors read `dashboardPeriodIndexes/current`. The first request after deployment builds this compact index from shop month keys and active imports. Shop and import mutations refresh it alongside dashboard summaries. While dirty, reads fall back to projected source queries; retry pending dashboard projection jobs if it stays dirty. The index is server-only and has a size cap, so very large datasets continue to use projected reads.

Period-selector refreshes read only affected shop documents. Shop edits and roster changes retain cached imports; import registration, undo and removal replace all active import entries for the affected months, including imports for other shops superseded or reactivated by that operation. Scoped import queries use equality filters on `status` and `month`, then preserve the existing descending `createdAt` and document-ID order in memory. These equality filters use [Firestore index merging](https://firebase.google.com/docs/firestore/query-data/index-overview#use_index_merging) with the existing single-field indexes; no new composite index is required. Shop deletion and all-data cleanup refresh all active imports so legacy report-date fallbacks reflect deleted performance sources. Older pending jobs without an import-change scope use full source scans. Concurrent dirty markers union affected shops and import months, and refresh tokens/document versions prevent obsolete owners from clearing newer work. Missing, invalid, legacy or oversized compact baselines retain full scans and the existing pending-job repair path.

Any future mutation that moves an import between reporting months must include both the previous and new months in its refresh scope, including when it also changes status. Direct source edits outside the application require a full projection refresh; a scope cannot repair changes in unspecified months.

Supervisor-filtered dashboard pages use the composite indexes in `firestore.indexes.json` and cached supervisor summaries in each `dashboardSummaries/{month}` document. Deploy the indexes before the application change with `firebase deploy --only firestore:indexes --project YOUR_PROJECT_ID` from the repository root, replacing `YOUR_PROJECT_ID` with the intended Firebase project ID. This repository has no `.firebaserc`, so select the project explicitly. Until an index is ready, the page falls back to reading the matching shop summaries. Older month summaries populate the supervisor aggregates on first filtered access.

Admin text search reads `dashboardSummaries/{month}/metadata/searchIndex`, a compact copy of shop totals. It is written atomically with the month summary and built on first search for older months. If the index exceeds 750 KB or is unavailable, search falls back to reading matching shop summaries. The `metadata.entries` field is exempted from automatic indexing in `firestore.indexes.json` because no query uses that array.

Projection refreshes merge changed shop summaries into the validated compact month index instead of rereading every shop summary. Aggregates and representative ranks are recomputed from the merged values using the existing calculations and tie ordering. The transaction reads the current changed summaries, month metadata and search index, then writes metadata and search together; invalid, missing, mismatched or oversized baselines fall back to a full summary query in that transaction. Month-scoped source calculations read shop, performance and supervisor data in their summary-write transaction so concurrent source edits trigger retries. Full source rebuilds and bonus projection refreshes retain their existing separate write flow. Explicit month rebuilds and pending maintenance jobs remain available. These changes need only an application release; they add no Firestore rules, composite indexes or collections.

Imports are recorded before completion in the `imports` collection and their data, history, status, and activity event are committed atomically. Only the latest import for each month is `active`; earlier retained versions are `superseded`. Monitor imports that remain outside `active`, `superseded`, `undone`, or `removed` states.

Administrators can mark an active import as superseded from Manage imported Excel files. This updates its history status and removes it from active import metadata used by the dashboard period selector and latest-import undo. Performance records, shop data and finalized payroll snapshots remain stored; calculations continue selecting the latest retained performance version. No previous import is activated by this action, so a month may have no active import. Manual supersession records its actor and time with an activity event in the same transaction and refreshes the affected month's projections through the existing repair path. Undoing a later import preserves a previous version's manual supersession instead of activating it or an older version. Verify status persistence, English/Albanian confirmation, unchanged monthly/quarterly payroll, period-selector refresh, permissions and later-import undo in staging before application deployment. No Firestore rules or indexes need deployment.

## Import weight profiles

The shop and bulk Performance Excel importers choose weight profiles from the selected Reporting month. October, November and December 2026 use the Q4 2026 configuration. The initial reporting month continues to default to today's month; review it before importing an earlier report. Changing Reporting month or the Data as of cutoff date recalculates the selected quarter and profiles.

Weight profiles store an explicit `year` (2000–9999), `quarter` (1–4) and optional `group`. Manage weight profiles exposes these fields alongside the display name. Leave the group empty for a shared profile; use the same group across a shop's quarterly configurations. Matching groups ignores capitalization and repeated whitespace. The importer first uses the shop's assigned profile if its year and quarter match, then the matching profile in the assigned group, then a shared profile for that period. Profile names can change without changing this selection. All periods stores both year and quarter as `null`; it remains an assigned fallback when no matching quarterly profile is available. A profile from a different quarter or year is never used as a fallback.

Existing profiles with neither period field retain compatibility: names ending in `Qn YYYY`, such as `Q4 2026` or `Paskuqan Q3 2026`, supply their period and optional group until saved. Opening the manager fills these fields; saving writes explicit metadata through the existing authorized, Zod-validated actions. Explicit fields, including All periods and an empty group, always override names. No live backfill is required. Imports are blocked for missing or ambiguous matches, and profile saves reject another valid profile with the same normalized group, year and quarter. Duplication prepares an unsaved draft so its period or group can be changed before creating it. Updates submitted by an older client without period fields preserve the currently stored configuration.

Imports preserve existing shop profile assignments so a shared quarterly fallback does not erase the shop-specific configuration family. New shops receive the selected profile as their assignment. The selected metric settings and order are copied into the imported performance record, monthly shop data and quarter settings through the existing import path. Profile edits affect future imports only. Final-month payroll snapshots, dashboard and bonus projections, report selectors, import history and undo retain their existing snapshot, refresh and restoration behavior. This selection change requires only an application release; no Firestore rules or indexes need deployment.

## Performance diagnostics

Set the server environment variable `PERFORMANCE_METRICS_ENABLED=true` to opt into performance diagnostics, then restart or redeploy the application. Leave it unset or set it to `false` to disable diagnostics. This adds no Firestore collections, rules or indexes and needs no Firebase deployment.

Instrumented server reads and closing saves emit JSON log records with `event: "targeti.performance"`, `source: "server"`, a fixed operation name, environment, success/error outcome, elapsed milliseconds and estimated JSON result size in `serializedBytes`. The size is not the actual compressed network response, and these records do not count billed Firestore reads. Use Firestore monitoring and Query Explain separately to measure document/index reads. Serialization and logging add overhead while diagnostics are enabled; compare runs with the same setting.

Authenticated pages also report CLS, FCP, INP, LCP and TTFB through same-origin `/api/performance` batches. The endpoint requires a current session, validates request origin and a Zod body capped at 4 KB, and writes metric logs only. Session validation adds an authentication read for managed users, so exclude diagnostic uploads when comparing business-operation requests and reads. Samples contain a browser-generated metric ID, numeric value, fixed route category and mobile/desktop viewport category. Raw paths, shop IDs/names, query strings, actor identifiers and business data are excluded. Metrics describe the initial document load, classified from its navigation entry; documents initially loaded on login are skipped after client sign-in. Use server-operation timing and the browser Performance panel for subsequent client navigation. Upsert each metric by its ID when aggregating logs so later values for the same metric do not become duplicate samples. Diagnostics are best-effort and do not retry failed uploads.

For a baseline, use a production build in staging and record repeated cold and warm runs for dashboard search, month/shop switching, one achievement save/revert, draft autosave, finalization/reopening, bonuses, Procedures and Attendance. Compare server median/p95 duration and result size, requests per interaction and Firestore reads separately; segment document Web Vitals by route and viewport and evaluate their 75th percentile. Production speed and billed-read improvements require those measurements, not a passing local build.

The [2026-10-09 local production-build profile](performance-profile-2026-10-09.md) records signed-in dashboard/Attendance measurements, reversible interaction checks, method limitations and the next measured optimization targets. It does not establish hosted production performance or Firestore billing gains.

Dashboard search waits 300 ms after the last nonempty input change before requesting results; clearing the search is immediate. Month/supervisor changes do not show placeholder rows from a different scope. Achievement saves/reverts and month-specific target saves refresh one authorized shop document and only matching performance/dashboard/bonus query scopes; bulk settings changes retain the directory refresh. Source mutations still maintain the existing server projections and repair paths.

The dashboard shop table displays all matching rows without pagination. Keep its empty-data fallback stable and automatic page-index resets disabled: switching to an uncached supervisor or month temporarily clears the query data, and a new empty array on every render can repeatedly trigger TanStack Table state updates and freeze the browser. Verify supervisor selection and clearing on an uncached query, month changes, sorting and direct filtered-page reloads after dashboard table changes.

The main dashboard streams a cached preview while its server periods and summary queries finish. Preview queries are disabled, and preview controls stay inactive until the server hydration completes; a cold or differently filtered cache shows a loading status. Client dashboard queries enable after the first commit so existing cache entries can accept fresh server hydration before attempting a stale-data refresh. On the main dashboard, the sidebar period selector observes the same cache without issuing its own request. Period changes there update the URL and use the dashboard queries; Insights and Bonuses retain their server-navigation behavior. All existing mutation invalidations and projection repair paths remain in place.

The authenticated layout remembers the main dashboard month, search, supervisor and explicit sort/direction in memory. Shop overview return links, the brand and the Dashboard link reuse that view. Query cache and remembered navigation reset when the account, access scope or locale changes. A direct shop URL or new browser session defaults to the main dashboard. Dashboard controls read the URL, including browser back/forward, and the initial render does not rewrite it. Verify warm returns after the 30-second/60-second query stale times, cold/direct visits, search/clear, Shop ascending sort, supervisor/month changes, history navigation, achievement-save invalidation and locale changes before application deployment. This requires an application release only; no Firebase rules or indexes need deployment. Compare like-for-like production builds before claiming a navigation speed improvement.

Draft Daily Closing saves invalidate the saved shop/month's Daily Activity quantities and financial reports, including when navigation occurs during a save. They do not invalidate unchanged Daily Activity settings or attendance. Finalization/reopening retain their broader invalidation. The server still reads settings in the save transaction, and settings mutations and the closing Refresh control continue to refresh the settings query. Verify draft saves, date/shop switches during save, finalization/reopening, concurrent settings changes, achievement save/revert, monthly target changes and bulk settings changes in staging before application deployment.

## Daily Activity

Each shop has an independent Daily Activity page at `/shop/{shopId}/daily-activity?month=YYYY-MM`. Editors can configure any month without a Performance Excel import, enter that month's activity targets and weights, or copy a saved weight profile into the month's settings. Copied weights remain independent of later profile changes. Viewers can read activity and saved settings but cannot change them. Configuration stays in `shops/{shopId}/dailyActivityMonths/{month}` and does not change Performance targets, imported reports, quarterly settings, dashboard summaries, bonuses or payroll.

Saved Daily Activity settings supply the activity fields, monthly targets and weights in Daily Closing for the same shop/month. The closing client loads configuration through an authorized settings query, and the server reads it within the closing save transaction. A new metric introduced by a chosen profile becomes available to record in Daily Closing. Historical activity keys absent from the chosen profile retain their saved quantities and remain in the configuration with zero target and weight until an editor assigns values. This integration does not write Performance reports, Excel imports, `monthlyData` or payroll.

Monthly activity quantities sum raw activities from the selected month's saved Daily Closing records, including drafts and finalized closings. Reads use the document-name date range and contain at most 31 closing records. Recorded-day and included-draft counts plus the latest saved date show closing coverage; an absent closing is not evidence of a zero-activity day. Each metric's contribution is its eligible monthly quantity divided by its configured monthly target, multiplied by its configured weight. Recompute from quantities and the selected month's settings rather than summing percentages saved on individual closings. Weights must total 100%; a nonzero weight requires a positive target. Activity keys remain stable across labels and include configured custom metrics. Cash, BOSS, invoices, debts, unsubscribe amounts and attendance are excluded from this calculation. Shop totals do not establish representative attribution.

When a monthly Procedures summary exists, its overall procedure total supplies New Line (`newLine`) quantities and its MixMax total supplies the MixMax (`custom_mixmax`) quantities. These counts replace the corresponding Daily Closing quantities rather than adding to them, preventing duplicate counting. Each MixMax procedure contributes to both overall New Line and MixMax with their respective configured weights. The raw totals include Done, Pending and Negative records. Confirmed performance uses Done quantities for these two metrics; performance including pending uses Done plus Pending. Negative procedures contribute to neither score. Other metrics retain their saved Daily Closing quantities in both scores. The page shows procedure status totals and the pending KPI/performance impact in percentage points. If no Procedures summary exists for the month, saved Daily Closing quantities remain the fallback for these metrics. An existing empty summary supplies zero procedure quantities. Procedure data is read from the validated monthly aggregate rather than scanning individual records or relying on a visible filtered page.

Closing saves, finalization, reopening and corrections become visible after the month's activity query is refreshed. A date contributes its latest saved quantities once; reopening does not remove its quantities from draft-inclusive totals. Procedure saves, additions from Daily Closing, imports, deletions, restorations and undo restorations invalidate the same shop/month Daily Activity query alongside the Procedures queries. Daily closing finalization does not finalize the monthly activity report or payroll. Settings saves validate Zod schemas, require editor/shop access, check the expected revision, and commit the configuration with an activity event. Reads validate stored documents and require shop access. Shop/all-data deletion removes the independent configuration collection together with the shop's closing records.

Changing configuration alone does not autosave an untouched closing or create a recorded day: financial autosave compares editable activity quantities independently of configured zero-value fields and their order. Finalized Daily Closing views and generated summaries retain the saved target/weight/score snapshot, while Daily Activity recalculates the month's quantities using its current saved settings.

The existing deny-all Firestore fallback protects the new configuration collection; access is through authorized server actions. No Firestore rules or composite indexes are required, and no Firebase deployment is needed for this feature. Before application deployment, run typecheck, lint and build, then smoke-test a month with no Performance import, custom metrics, copied profiles and newly recordable profile metrics, retained historical quantities, draft/finalized/reopened closing updates, procedure status changes and double-count prevention, missing/empty Procedures summaries, procedure import/delete/restore/undo refreshes, conflicting settings saves, viewer/shop restrictions and mobile tables in staging. Application deployment remains a separate operation that must be explicitly requested.

## Attendance and original-format Excel export

Daily Closing places attendance first in the right column, followed by Procedures, Unsubscribe entries and Debt entries, minimized by default, in a content-sized card with a compact title and icon-only Save, Cancel, Undo and expansion controls in one header row. Icon controls retain translated accessible labels and tooltips. The daily Presence table shows first names and attendance cells only, omitting roles, manager icons, column letters, row numbers, the date column, and explanatory/missing-entry text. Names are shortened for display only; stored rosters and exports retain full names. Its Minimize/Expand control keeps the editor mounted so drafts survive minimizing; the unsaved reminder remains visible. Attendance has no separate planned/confirmed status. Older stored status fields are discarded when read and omitted from new writes.

Each shop has a Presence & Shifts page at `/shop/{shopId}/attendance`. The selected month's roster includes SM (manager), SR, and IE staff. SM names receive a manager label and visual emphasis. Staff IDs, names and roles are saved per month, preserving historical rosters independently of performance imports. Attendance does not alter performance, bonus eligibility, payroll or cash calculations.

The attendance grid uses a content-sized table with 144px staff columns and reduced row, legend and toolbar spacing, spreadsheet column letters, row numbers, compact attendance codes, a code legend, and frozen headers/date columns. Editors can change names and roles directly in the monthly column headers and add staff as new columns. Roster and attendance drafts share Save/Cancel and Undo; saving preserves staff IDs, checks the month revision, and records corrections through the existing authorized attendance action. Blank names and Other entries without text block saving. Daily Closing keeps roster headers read-only while attendance cells remain editable; viewers cannot edit either. Original-format exports still require a template with columns for every roster member.

Calendar rows and attendance cells are memoized, with cached date/day/staff lookups and footer totals calculated in one pass. Cell edits use stable callbacks and an atomic draft/undo reducer; unchanged rows and cells can keep their rendered output. This does not change stored attendance, locking, roster order, exports or save validation. Before application deployment, verify keyboard focus and dropdowns while editing, Other notes, clearing entries, Undo/Cancel, bulk entry, previous-week copying, roster changes, daily/viewer views and concurrent saves in a signed-in staging session. Profile the real controls in a production build before claiming a browser performance improvement.

Editors can move staff columns left or right with the arrows in the monthly column-letter headers. Save persists the roster array order for that shop/month; Undo and Cancel also cover moves. Attendance entries and draft values remain linked by staff ID, and Daily Closing uses the same saved order. Reordering alone records a roster correction with each moved person's previous/new staff column position (starting at 1); older history without positions remains readable. The date column stays fixed. Original-format Excel exports retain the template's column mapping and physical layout rather than following the app's display order.

Shift cells have no Add note link. Existing imported notes remain visible as text; Other entries retain their required text field and monthly bulk entry still supports notes.

The color key is collapsed by default in both attendance views and can be expanded with its keyboard-accessible disclosure. Attendance cell colors and the color key share one mapping: Turn 1 blue, Turn 2 violet, both turns teal, weekly day off slate, annual leave amber, medical leave rose, and Other/support orange. Codes remain visible so color is not the only indicator. Colors update with drafts in both attendance views, include dark-mode equivalents, and do not change saved attendance values or the original Excel template's formatting.

Sundays have a pale orange row background, orange date marker and tinted row number. Empty staff cells share the Sunday tint; entered attendance keeps its status color. Sunday is included in the monthly color key and does not imply a weekly day-off entry.

`shops/{shopId}/attendanceMonths/{month}` stores the roster, revision, and private template mapping. `attendanceDays/{date}` stores entries and audit timestamps. Month reads are limited to 31 attendance documents. Saves validate Zod schemas and actor/shop access, check both the month revision and individual day versions, and commit records with an activity event. The existing catch-all Firestore rule denies direct client reads/writes to these new collections; access is through authorized server actions/routes. No new rules or composite indexes are required.

Daily Closing shares the same attendance records. Attendance has explicit Save/Cancel controls, separate from financial autosave. Save or cancel attendance edits before finalizing. Finalization copies attendance entries into the closing atomically; attendance remains editable in both views after finalization. Attendance edits, staff changes and template imports do not require reopening a closing. The closing retains its attendance snapshot from finalization; later attendance corrections are reflected in the attendance views and original-format exports. Missing attendance produces a reminder without blocking older closing workflows.

An editor uploads an XLSX workbook of up to 2 MB, reviews staff mapping and the selected sheet, and approves the import. The workbook must belong to the selected shop and use monthly Albanian worksheet names including a year, DATA in B5, SM/SR/IE roles on row 5, staff names on row 6, and calendar dates in column B from row 7. Imports replace the selected month's attendance only after revision checks, regardless of closing status. Nonstandard attendance text is retained verbatim until edited. An existing sheet can also be attached as a blank template for a different empty month; exporting then adds that new month while preserving all original sheets.

When a month has no template, editors can use the previous month's saved template without uploading the workbook again. The authorized action maps columns to the current roster by stable ID or a unique name match ignoring case and accents, rejects incomplete/ambiguous mappings, and validates the target export before attaching the immutable saved template reference. The current roster order and all attendance days remain unchanged, including populated months. The month revision protects concurrent changes, and attaching the reference records a template-change history event. Export adds the target monthly sheet using the existing calendar-cloning path and preserves the source workbook's sheets and formatting.

Original files are stored privately in `attendanceTemplates/{version}/chunks` beneath the shop, with chunks smaller than Firestore's document limit. Historical template versions are retained until shop/all-data deletion, which also recursively removes all attendance collections. Never commit template workbooks, log staff/medical notes, or include workbook contents in error monitoring. Export uses the original XLSX package and selectively changes mapped cells, preserving styles, conditional formatting, merges, dimensions and print settings. A larger roster requires a matching template; columns are never silently inserted. Verify exported files in Excel and compare print preview before production rollout. Structural package comparisons alone do not establish native Excel rendering.

History is available from Presence & Shifts; Daily Closing omits the history shortcut. Successful attendance saves, roster updates and Excel imports append immutable events in `attendanceMonths/{month}/history/{revision}` within the same transaction as the changes. Each event records actor ID/name, timestamp, source and changed dates; `details/{date}` and `details/roster` retain only changed before/after values and staff names at the time of the change. Unchanged entries and failed/conflicting saves produce no correction events; attaching a template is recorded even when entries match. Revisions are padded document IDs for newest-first cursor pagination (20 events plus one lookahead), using the built-in document-name index. Details load on demand with at most 32 documents, keeping imports within Firestore document limits. Both reads validate Zod schemas and require shop access, including for viewers. No client write/delete path is exposed and no new indexes/rules are required. Shop/all-data deletion removes history recursively with attendance months. History begins at rollout; earlier activity logs do not contain before/after attendance values and are not backfilled. Closing finalization itself does not count as a correction. Smoke-test edits, clearing entries, notes, roster updates, template imports, pagination, concurrent-save rejection, viewer access and mobile history tables in staging.

Before application deployment, run typecheck, lint and build, then smoke-test import/mapping, month/week edits, Daily Closing Save/Cancel/finalize/reopen, concurrent saves, viewer restrictions, mobile horizontal scrolling, and original-format export in staging. This feature introduces no Firebase rules/index deployment. Application deployment and production template import remain separate operations.

## Procedures

Each shop has `/shop/{shopId}/procedures?month=YYYY-MM`. Its editable grid follows the supplied New Line workbook: Order Number, Name, ID, Product, Date, User, Status, with yellow clock icons for pending, green check icons for completed and red X icons for negative. Status cells show icons only; tooltips and accessible names retain translated status labels. The editable status menu offers icons with translated labels and supports keyboard selection. Deleted records and viewer cells use the same icons. The compact monthly summary has MixMax and TRY&BUY rows, Total/Done/Pending/Negative columns, and a totals footer. It counts all saved records, including pages not currently visible. Blue/violet dots identify products; green/yellow/red dots identify status columns. The Done column has a subtle green tint across its header, product rows and total, with matching dark-mode shades. Nonzero pending counts receive a soft yellow highlight, while zero remains neutral. TRY&BUY completed equals overall completed minus completed MixMax; each product's negative count equals its total minus completed and pending. Summary validation requires these derived counts to be nonnegative. This same layout is used in import review. Products are MixMax and TRY&BUY. Edits use Save/Cancel, and stale record revisions reject overwrites. The User column displays full representative names and edits them through the same roster dropdown as the add form. Historical or ambiguous names remain available as their current value; customer names remain full. Product/status dropdown arrows and the date picker icon are hidden to keep cells compact; Product, Date, User and Status use reduced column widths while retaining editable controls and accessible labels. The table displays and edits only dates; changing a date preserves its stored time. Dates and times are stored as local business times, without timezone conversion.

Daily Closing has a minimized Procedures form with required order number, customer name, customer ID, product and staff user. User is a required sales-representative dropdown from the selected shop's performance roster for the closing month, falling back to its default sales representatives only when no monthly roster exists. Selection starts blank; an empty roster blocks adding entries and displays guidance. New entries send the representative ID, which the server validates against the current shop/month roster inside the save transaction and resolves to its stored name. Imported historical names remain preserved, and editors can assign a current representative through the table dropdown. Add procedure saves immediately with pending status against the selected closing date; it does not wait for financial autosave. Save or cancel the entry before changing dates or finalizing. Procedures remain independently editable in their monthly table after finalization. They do not change cash, imported Performance reports, bonus eligibility or payroll. The independent Daily Activity page uses their monthly totals and statuses for its confirmed and including-pending New Line/MixMax performance as documented above.

The Procedures page also shows this form expanded beneath the monthly summary for editors. Its date picker is limited to the selected month and starts at today's Albanian business date for the current month, or the first day for another month. Changing the entry date preserves typed fields and the representative selection. Add procedure uses the same authorized, roster-validated immediate save and refreshes all Procedures pages and Daily Activity totals, returning the table to page one with its current filters and sorting. Save or cancel table edits before entering a procedure; add or cancel an entry before changing the month, filters, sorting or table page. Viewers retain the read-only table and summary without an entry form. Daily Closing retains its minimized form and selected closing date.

Press the User column header to cycle through ascending user names, descending user names and original source order. Sorting applies to the entire selected month and current product/status filter before pagination, using case- and accent-normalized names with a stable record-ID tie-breaker. Sort changes reset pagination and row selection; sorted saves return to page one because edited users can move between pages. Summary counts remain for the entire month. Sorted query keys include the sort mode, and cursors bind the shop, month, filter and direction to the saved ordering boundary, so deleting or editing the boundary record does not invalidate that cursor.

Sort, filter and page changes within the same shop/month keep the current table mounted while the next result loads, preserving its scroll position. The Reload icon spins and the table announces its busy state; placeholder rows cannot be edited or selected. Changing shops or months never carries forward another scope's rows. Verify both sort directions while scrolled, filter/page loading, and month changes with a delayed response before application deployment.

The Procedures table uses a stable empty-data fallback and TanStack Table's manual pagination mode because server cursors already select its rows. This disables automatic page-index resets when query data changes; the existing cursor handlers still reset the page and selection after month, filter, sort and relevant mutation changes. Keep these safeguards when changing loading or empty-table behavior to avoid repeated internal table state updates.

User names resolve against the selected month's performance roster, with the same default-roster fallback as the add form. Case/accent differences, dotted/underscored/hyphenated usernames, a repeated appended surname, and a unique first-name-only alias match only when exactly one roster representative qualifies. Unknown names, conflicting surnames and ambiguous first names remain unchanged. The table, its User dropdown, the add form and the filter use these full roster names. Raw imported names remain stored for provenance and unchanged edits; filtering and sorting use derived canonical keys, so all aliases for a recognized representative share one filter option across every page. `userNameIndexRosterHash` fingerprints the roster plus normalization version; changes rebuild the existing sort/filter projections in transactions of at most 200 records. Each batch checks that the roster still matches its fingerprint. Backfill preserves record revisions, source fields, audit timestamps and all monthly totals. No Firestore rules or composite indexes require deployment. Verify grouped aliases across pages, both sort directions, unknown/ambiguous names, roster changes, assigning a different representative, and non-User edits preserving original names before application deployment.

The toolbar's All users dropdown groups records by the same monthly representative names as the table and add form, including aliases across every page. Historical/imported names absent from the current roster remain separate options. Product/status summary buttons retain a selected User filter; the overall total and Clear filter clear all filters. Summary counts remain for the whole month, and button labels describe filtering for the selected user. Query keys and ordering cursors include User; saves under a User filter reset to page one. After a successful User correction, the selector follows the corrected saved name, retaining product/status filters. A batch corrected to several different names clears only the User filter to show the corrected rows; unchanged names and failed/canceled saves keep the selection. Original names remain options while records still use them. A selected user whose last record is deleted remains visible in the dropdown until the filter is changed or cleared. Unsaved drafts disable filter changes. Editors and viewers can filter.

`userTotals` in the validated month summary supplies the complete User dropdown without scanning visible table pages. Stored counts retain raw imported names; page responses group these counts by resolved representative name and return the authoritative monthly roster for both dropdowns. This preserves Tailwind 3 and the existing glob consumers; normal glob expansion and deeply nested input rejection must be checked after changing this override. It bounds nesting, not all possible resource consumption.

Track the [upstream fix](https://github.com/micromatch/braces/issues/70) and replace this temporary fork with an upstream patched release when available. Do not remove the override merely to silence npm resolution warnings. Run a clean Node 22/npm 10 install, `npm run typecheck`, `npm run lint`, `npm run build`, and `npm run audit` after dependency changes. ## Deployment checklist

1. Confirm the target environment and Firebase project ID.
2. Confirm the latest Firestore backup completed and staging restore is healthy.
3. Run `npm ci`, `npm test`, `npm run build`, and `npm run audit`.
4. Deploy Firestore rules and indexes to staging, then deploy the application.

6. Promote the same commit and configuration shape to production.
7. Watch errors, pending maintenance jobs, latency, and import failures for 30 minutes.

## Rollback checklist

1. Stop new imports and destructive administration.
2. Roll the application back to the last known-good release.
3. Roll back rules only when they remain compatible with data written by the failed release.
4. Run dashboard-summary rebuilds for affected months.
5. Restore Firestore only after impact analysis; prefer targeted repair because a full restore can overwrite valid concurrent changes.
6. Document the affected release, time window, shops/months, repair actions, and verification.
